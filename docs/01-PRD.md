## 1. 产品概述

### 1.1 背景

企业中大量汇报、方案、咨询类 PPT 的制作流程是：拿到一份 PDF/DOCX 主材料 → 套用公司模板 → 人工提炼、排版。该过程重复度高、耗时长（一份 30 页汇报通常需要 0.5～2 个工作日）。

本产品将该流程自动化：**用户提供 PPT 模板 + 主说明文档 + 页数 + 模式 + 内容密度共 5 项输入，系统在分钟级时间内产出可编辑、可交付、符合事实的 PPTX 文件**，并支持在线预览、失败重试、过程可追溯。

### 1.2 核心理念

> AI 负责理解、规划、提炼和编排；python-pptx 负责模板复用、坐标控制、字体、图形、图表和最终 PPTX 渲染。

- 不让大模型直接生成 PPT XML 或控制最终页面坐标；
- AI 输出统一的中间层 **Presentation JSON**，由确定性的 Renderer 渲染；
- 所有边界条件由独立的 **Guard 层** 统一校验，不分散在各 Agent 中。

### 1.3 产品定位与竞争力

核心竞争力不是"能生成 PPT"，而是：

> **在严格控制事实、页数、模板、布局和视觉质量的情况下，稳定生成可编辑、可追溯、可迭代的专业 PPT。**

| 维度 | 本产品 | 通用 AI PPT 工具 |
|---|---|---|
| 模板 | 复用用户自有 .pptx 模板（保留 Logo/字体/配色/页脚） | 内置固定模板 |
| 事实 | Fact Registry + 来源追溯，禁止编造 | 无事实约束 |
| 可编辑性 | 原生 PPTX 元素（文本框/原生图表/原生 Shape） | 常见整页图片，不可编辑 |
| 可靠性 | Guard 层 + Fallback Matrix + 分页级兜底 | 单点失败即整体失败 |
| 部署 | 全容器化，可私有化部署 | 仅 SaaS |

### 1.4 目标用户

| 角色 | 场景 | 诉求 |
|---|---|---|
| 企业员工 | 周报/项目汇报/内部草稿 | 快（极速模式）、不出错 |
| 售前/咨询顾问 | 客户方案、建设方案 | 专业（专业模式）、事实准确、模板合规 |
| 部门管理者 | 向上汇报 | 质量高、逻辑清晰、可继续编辑 |
| 系统管理员 | 私有化运维 | 容器化部署、可观测、可扩容 |

## 2. 术语表

| 术语 | 含义 |
|---|---|
| 主说明文档 | 用户上传的 PDF/DOCX，是 PPT 内容的唯一事实来源 |
| 模板 | 用户上传的 .pptx，提供视觉语言（母版/配色/字体/Logo/版式页） |
| Knowledge Model | 主文档解析后的结构化知识模型（章节/事实/数字/图表数据） |
| Fact Registry | 事实注册表，登记所有关键事实及其来源页码与置信等级 |
| Presentation JSON | AI 规划输出的中间层数据，Renderer 的唯一输入 |
| Guard 层 | 独立校验层：InputGuard / FactGuard / PageGuard / ContentGuard / LayoutGuard / RenderGuard 等 |
| Page Budget | 页数预算引擎，将目标页数分配为固定页+章节页+正文页 |
| 内容密度 | 单页信息量档位：紧凑（low）/ 标准（medium）/ 充实（high） |
| Vision QA | 将 PPT 渲染为图片后用多模态模型做视觉质检 |
| Job | 一次 PPT 生成任务，异步执行，可查询、可重试 |
| Stage | Job 内的一个阶段（解析/大纲/内容/渲染/质检…），有独立起止时间与耗时 |

## 3. 产品目标与成功指标

### 3.1 核心目标

1. **完成率优先**：在输入合法的前提下，任务最终产出 PPTX 的成功率 ≥ 99%（含降级产出）。
2. **事实底线**：正式内容中的关键数字/事实 100% 可追溯至原始文档；系统绝不编造事实。
3. **速度目标**（生产环境，5～10 并发 Worker）：

| 页数 | 极速模式 | 标准模式 | 专业模式 |
|---:|---|---|---|
| 10 | 20～40s | 40～90s | 1～3min |
| 20 | 40～70s | 1.5～3min | 2～5min |
| 30 | 60～100s | 2～4min | 3～8min |
| 50 | 2～3min | 4～7min | 6～12min |
| 100 | 4～7min | 8～15min | 12～25min |

4. **可交付质量**：专业模式质量分（100 分制）≥ 85；标准模式 ≥ 75。
5. **可运维**：全容器化一键部署（docker compose up），核心链路可观测（阶段耗时、LLM 调用、错误码）。

### 3.2 北极星指标与 KPI

| 指标 | 定义 | 目标 |
|---|---|---|
| 任务成功率 | 成功产出 PPTX 的 Job / 总 Job | ≥ 99% |
| P90 生成耗时 | 各模式各页数档 P90 耗时 | 见 3.1 表 |
| 事实追溯率 | 正式页面中带来源标注的关键事实占比 | 100%（专业模式） |
| 首次可用率 | 无需人工修改即可交付的比例（抽检） | ≥ 70%（专业模式） |
| 失败可解释率 | 失败 Job 中带明确错误码与原因的比例 | 100% |
| 重试成功率 | 失败后重试成功的比例 | ≥ 80% |

## 5. 功能需求

### 5.1 FR-1 输入管理（5 项核心输入）

一次生成任务的输入固定为 5 项：

| # | 输入 | 类型 | 约束 | 默认值 |
|---|---|---|---|---|
| 1 | PPT 模板 | .pptx 文件 | ≤ 50MB；可解析；支持选择历史模板或内置默认模板 | 系统默认模板 |
| 2 | 主说明文档 | .pdf / .docx | ≤ 100MB；≤ 500 页；可解析出有效文本（否则走 OCR） | 必填 |
| 3 | 页数 | 整数 | 5～100 页；与章节结构冲突时触发 Page Budget Conflict 交互 | 系统按内容量推荐 |
| 4 | 模式 | 枚举 | fast（极速）/ standard（标准）/ premium（专业） | **fast（极速）** |
| 5 | 内容密度 | 枚举 | low（紧凑）/ medium（标准）/ high（充实） | medium |

**输入校验（InputGuard，上传后立即执行）：**

- 文件类型/大小/完整性检查 → 解析试读 → 内容统计（字数、页数、图片数、表格数）；
- PDF 无有效文本 → 自动判定扫描件 → 走 OCR 流程并提示"OCR 结果的关键数字将进入事实核验"；
- 模板无法解析 → 提示更换或使用系统默认模板；
- 加密/损坏文件 → 明确报错（错误码），禁止"解析失败 → AI 编内容"。

**内容量预检：**

- 系统按密度估算合理页数区间；资料不足以支撑目标页数时提示三选项：`[压缩至推荐页数] [继续生成] [补充资料]`；
- 用户坚持继续时标记 `content_confidence = low`，允许通过拆解/重组/可视化/流程化增加表达页数，但**禁止编造事实**；
- 资料远超页数（如 500 页 PDF 生成 10 页）时按重要性评分保留高价值信息。

### 5.2 FR-2 生成任务（异步 Job）

- 提交后立即返回 `job_id`，后台异步执行（绝不做同步长阻塞接口）；
- 任务全生命周期状态可查询：排队 → 各阶段执行中 → 成功/失败/已取消；
- 进度推送：前端通过 SSE（降级为轮询）获得阶段级 + 页级进度；
- **边生成边看**：单页内容生成完成即推送该页结构化内容卡片；渲染完成后推送缩略图；
- 支持取消执行中的任务；
- 同一用户并发任务数可配置（默认 3），超出排队。

### 5.3 FR-3 三种模式（核心差异化需求）

三种模式必须是**三条不同的流水线实现**，而不是同一条流水线加开关。总原则：**在保证"完成生成 + 符合事实"的前提下，尽可能快地生成高质量可交付 PPT**。

| 能力 | ⚡ 极速模式（默认） | 🚀 标准模式 | 💎 专业模式 |
|---|---|---|---|
| 定位 | 内部草稿、快速汇报 | 日常正式汇报 | 对外方案、领导汇报、咨询报告 |
| 文档理解 | 规则解析 + 单次 LLM 摘要 | 结构化知识建模 | 深度知识建模 + Fact Registry + RAG |
| 大纲 | 大纲+页面规划合并为 1 次调用 | 独立 Outline Agent + OutlineGuard | Outline Agent + Guard +（可选）用户确认 |
| 页面内容 | 按章节批量生成（1 章 1 次调用），章节间并行 | 页级并行生成 | 页级并行 + RAG 逐页取证 + 来源标注 |
| 模板匹配 | 规则直配（类型表查找） | 打分匹配（类型/元素/长度/均衡） | 打分匹配 + 密度自适应换版 |
| 事实保障 | 关键数字校验（正则+比对） | 关键事实抽取与比对 | 完整 Fact Registry + 冲突交互 + 等级管控 |
| 布局 QA | 规则校验（字数预算/溢出估算） | 规则 + 实测文本度量（Pillow） | 规则 + 度量 + Vision QA（多模态模型） |
| 自动修复 | 仅确定性修复（压缩/换版式），0 轮 LLM 修复 | ≤ 1 轮修复 | ≤ 3 轮修复闭环 |
| 预览产物 | PPTX + 整套缩略图 | PPTX + 缩略图 + PDF | PPTX + 缩略图 + PDF + 质检报告 + 来源清单 |
| 推荐模型 | qwen-flash / deepseek-chat | qwen-plus / deepseek-chat | qwen-max + deepseek-reasoner + qwen-vl-max |
| LLM 调用量（10 页参考） | 3～5 次 | 12～16 次 | 25～35 次 |
| 目标（10 页） | 20～40s | 40～90s | 1～3min |

**模式共同底线（任何模式不得突破）：**

1. 必须产出可打开、可编辑的 PPTX（允许降级版式，不允许产出损坏文件）；
2. 关键事实不得编造，数字冲突不得由 AI 自行取舍；
3. 页数满足硬约束（或经用户确认调整）；
4. 阶段耗时全程记录。

### 5.4 FR-4 内容密度

密度作用于 Page Budget、单页文案预算与版式选择：

| 参数 | low 紧凑 | medium 标准 | high 充实 |
|---|---:|---:|---:|
| 单页正文字数预算 | ≤ 120 字 | ≤ 180 字 | ≤ 240 字 |
| 单页元素数（卡片/条目） | 2～3 | 3～5 | 4～6 |
| 每千字资料建议页数 | 2.5 页 | 2 页 | 1.5 页 |
| 版式倾向 | 大字报/金句/单图 | 均衡 | 多栏/卡片/图文混排 |

密度只是软约束（Soft Constraint）：文案超预算触发"压缩 → 换版式 → 拆页 → 重平衡"，禁止把字号缩到不可读（正文最小 12pt）。

### 5.5 FR-5 事实保障

- 所有关键事实（金额、人数、数量、面积、日期、增长率、技术参数）进入 Fact Registry，登记来源文件与页码；
- 事实等级：A（原文明确）/ B（多处交叉验证）/ C（AI 推导，谨慎使用并标注）/ D（AI 猜测，默认禁止）；
- **数据冲突**：同一事实多来源不一致时建立 Conflict Registry，专业模式弹出选择交互（`[用 1.2 亿] [用 1.5 亿] [都不使用]`）；极速/标准模式默认策略为"取最新来源并在备注页声明"，可配置为"跳过该数字"；
- 图表数据必须做单位统一（亿/万混用归一）、空值处理（缺失不得自动当 0）、极端值检查；
- 每页保存 `sources`（来源文档+页码），支持"这页数据来自哪里"查询。

### 5.6 FR-6 兜底与降级（边界处理）

系统必须内置 Fallback Matrix，任何单点异常不导致整体失败：

| 异常场景 | 一级兜底 | 二级兜底 | 最终策略 |
|---|---|---|---|
| 模板缺目标版式（如无 architecture 页） | 近似版式匹配 | 系统标准版式 | 原生 Shape 动态绘制 |
| 模板只有封面 | 提取 Logo/配色/字体/背景 | 系统 Layout 生成正文 | 默认模板 |
| PDF 无文本（扫描件） | OCR | Vision 模型识别 | 提示用户补充可编辑文档 |
| 图片处理失败 | 使用原图 | SVG 生成 | 图形占位 + Warning |
| 图表数据异常 | 数据清洗后原生 Chart | 降级为表格 | 文字要点 + Warning |
| AI 返回非法 JSON | 自动重试（换 Provider） | JSON 修复器 | 该页降级为 title_content 版式 |
| 单页内容过长 | 压缩改写 | 换高容量版式 | 拆页 + 全局页数重平衡 |
| 页数预算冲突（章节数 > 可用页数） | 提示用户四选项 | 合并章节页 | 章节标题嵌入正文页 |
| 中文字体缺失 | Noto Sans CJK | Source Han Sans | 默认字体 + Info 记录 |
| 单页生成失败（重试后仍失败） | 该页降级为大纲要点页 | 占位页 + 明显标记 | 不阻塞整体产出，报告中标注 |
| LLM Provider 故障 | 自动切换备用 Provider（qwen ⇄ deepseek） | 降级模型档位 | 任务失败 + 明确错误码 |
| LibreOffice 转换失败 | 重试 1 次 | 跳过预览（仅缩略图降级） | PPTX 正常交付 + Warning |

所有自动兜底行为必须记录（Info/Warning 级），在质检报告中可见。

### 5.7 FR-7 失败处理与重试

- **失败必须可解释**：每个失败 Job 必须带有 `error_code`（错误码枚举，见实现方案 §7）、`error_message`（用户可读原因）、`failed_stage`（失败阶段）；
- 错误分级：
  - **Blocker**（任务失败）：输入无法解析、PPTX 无法生成、页数硬约束无法满足且用户不允许调整、所有 LLM Provider 均不可用；
  - **Warning**（继续但报告）：页面偏密、模板匹配度低、图片质量一般；
  - **Info**（记录自动处理）：使用了 Fallback 模板、自动压缩了文案等；
- **重试**：
  - 支持一键重试，默认**断点重试**（从失败阶段继续，复用已完成阶段的产物/checkpoint）；
  - 支持"从头重新生成"（新 Job，关联原 Job 形成版本链）；
  - 单阶段内部自动重试：LLM 调用失败自动重试 ≤ 2 次（含切换 Provider），渲染/转换失败自动重试 1 次；
  - 重试次数、每次失败原因均留痕。

### 5.8 FR-8 存储与在线预览

- 产物统一上传对象存储，**存储层抽象**：默认 MinIO（私有化），可配置切换阿里云 OSS（S3 兼容协议，一套代码）；
- 产物包括：`final.pptx`、`preview.pdf`、逐页 `page-{n}.png` 缩略图/大图、`report.json` 质检报告、中间产物（Presentation JSON、Knowledge Model）；
- **在线预览**：基于逐页 PNG 的翻页预览（不依赖 Office 在线服务，内网可用）；提供 PDF 预览与下载作为补充；
- 下载通过预签名 URL（有效期可配置，默认 1 小时），不经业务服务中转大文件；
- 产物保留策略可配置（默认 30 天，中间产物 7 天）。

### 5.9 FR-9 全链路耗时记录

- Job 级：`created_at`（提交）、`started_at`（开始执行）、`finished_at`（结束）、`queue_ms`（排队耗时）、`duration_ms`（执行耗时）；
- Stage 级：每个阶段记录 `stage_code`、`started_at`、`finished_at`、`duration_ms`、`status`、`attempt`（第几次尝试）；并行阶段记录各分支耗时与汇聚耗时；
- LLM 调用级：每次调用记录 provider、model、输入/输出 token、耗时、是否成功（用于成本与性能分析）；
- 前端进度页与任务详情页可视化展示各阶段耗时；管理端可按模式/页数聚合分析。

### 5.10 FR-10 模型对接（国内模型优先）

- 一等公民 Provider：**Qwen（DashScope）** 与 **DeepSeek**；架构上通过统一 LLM Gateway 接入，后续可扩展 GLM、Kimi 等；
- 任务级路由（可配置）：

| 任务 | 首选 | 备选 |
|---|---|---|
| 文档理解/摘要 | qwen-plus | deepseek-chat |
| 大纲规划 | deepseek-chat | qwen-plus |
| 页面文案（批量/页级） | qwen-flash（极速）/ qwen-plus（标准+） | deepseek-chat |
| 复杂推理（专业模式规划/修复） | deepseek-reasoner | qwen-max |
| 结构化 JSON 输出 | qwen-plus（JSON mode） | deepseek-chat |
| Vision QA / OCR 辅助 | qwen-vl-max | qwen-vl-plus |
| Embedding（RAG） | text-embedding-v3（DashScope） | bge-m3（本地） |

- Provider 级熔断与自动切换；全部模型参数（key、base_url、模型名、超时、限流）通过环境变量/配置中心管理，不写死。

### 5.11 FR-11 任务历史与版本

- 任务列表：按状态/模式/时间筛选，展示缩略图、耗时、质量分；
- 重新生成形成版本链（v1/v2/v3…），历史版本可下载、可对比基础信息；
- V1 范围内提供 Job 级重新生成；单页/单章重新生成列入 V2 路线图。

## 6. 非功能需求

| 类别 | 需求 |
|---|---|
| 部署 | 全容器化（前端、API、Worker、Redis、PostgreSQL、MinIO、LibreOffice 均为容器）；docker compose 一键部署；支持后续 K8s |
| 性能 | 见 §3.1 速度目标；API P99 < 500ms（不含生成任务本身）；单 Worker 内存 < 2GB |
| 并发 | 默认支持 10 个并发生成任务；Worker 水平扩容即可线性提升 |
| 可用性 | 单任务失败不影响其他任务；Worker 崩溃后任务可被重新调度（幂等阶段设计） |
| 可观测 | 结构化日志（含 job_id/stage 贯穿）；Prometheus 指标（任务数、成功率、阶段耗时、LLM 耗时/token）；Grafana 看板 |
| 安全 | 文件类型白名单 + 内容嗅探；上传隔离存储；预签名 URL 限时访问；API Key 服务端保管；（V1 单租户，预留 user_id 字段支持多租户） |
| 字体 | 容器内置 Noto Sans CJK / Source Han Sans，Font Resolver 处理字体缺失映射 |
| 数据 | 生成过程数据可追溯（Presentation JSON、阶段 checkpoint 留存 7 天）；用户文件默认 30 天清理 |
| 兼容 | 产出 PPTX 兼容 Office 2016+ / WPS；不使用 python-pptx 不支持的高级特性（复杂 SmartArt、动画） |

## 7. 范围边界（V1 明确不做）

- PPT 动画、切换效果；

- 移动端适配（V1 桌面 Web 优先）。
